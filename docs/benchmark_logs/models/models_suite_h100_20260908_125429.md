# H100 全模型基准套件（2026-09-08，short 128 / medium 4k / long 32k × 三方引擎）

驱动：`rapid_llm.benchmark.models`（由 `benchmarks/suites/run.py models` 编排），suite 索引
`models_suite_h100_20260908_125429.json`。4 模型 × 3 场景 × 可用引擎，36 次引擎运行，
35 成功 + 1 记录型 OOM（30B bf16 long 的 transformers 运行，本质性显存不足，见"运行注记"）。

## 环境与口径

- 2 × NVIDIA H100 80GB HBM3（驱动 580.126.20，CUDA 13.0），显存预算 0.92 × 实测容量
- rapid_llm / transformers：rapid_llm `.venv`（torch 2.13.0+cu132 / transformers 5.15.1 / Python 3.14）
- vllm：`/mnt/otto-temp/zhanghonggao.zhg/vllm/.venv`（vllm 0.28.0，torch 2.13.0+cu132），
  以该解释器独立子进程运行（子进程内不 import rapid_llm）
- 数据：`random-ids`（RandomDataset 词表整数序列 + vLLM 同款 decode→re-encode 长度校正，
  三档实测 EXACT 零漂移），greedy，batch 8，iters 2（取吞吐中位轮），ignore_eos
- rapid_llm 生产默认三件套：`use_cuda_graph=True`（引擎默认）+ `enable_prefix_cache=True`
  （显式开，对齐 vllm 默认）+ chunked prefill（引擎默认，KV fp8 时自动关）；完整 engine args
  记入各 JSON 的 `results.<engine>.engine_args`
- 场景：short 128/32/msl 4096，medium 4096/128/msl 8192，long 32768/256/msl 33792
  （Qwen2.5-0.5B 的 `max_position_embeddings=32768`，long 档输入收缩为 31744/32768）
- 指标：TTFT/TPOT p50/p99 为逐请求分位数（rapid_llm：引擎逐请求 monotonic 时间戳；
  vllm：v1 `RequestStateStats` 的 `first_token_ts−queued_ts` 与逐 decode gap；两者口径同构）。
  transformers 为 batch 级均值（无逐请求计时），标 `*`
- TP 决策：取最小 TP 满足 权重/TP + KV/TP + 激活(4GB) ≤ 0.92×79.6GB；除 30B bf16 long
  需 TP2 外全部 TP1

## 读法

- **short 档 rapid_llm 两次夺冠**：0.5B 2775 vs vllm 1975（1.41×）、4B 1274 vs 1483
  （0.86×）、30B 645 vs 804（0.80×）。TTFT 同量级（小 prefill 两端都快），差距在 decode：
  short 档上下文 ≤ 160 token，rapid_llm 的 decode CUDA graph 全程 replay（71 次），
  TPOT 与 vllm 持平甚至更低（0.5B 1.57 vs 2.93 ms）。
- **medium/long 档 rapid_llm 的 TPOT 恶化 3–8×，主因是 decode graph 失效**：
  引擎按 `seq_len_buckets=(256,512,1024,2048,4096)` 捕获 decode graph，medium 档
  context 一旦超过 4096 即回退 eager（graph_replays 2 次），long 档全程 eager（0 次）。
  0.5B medium TPOT 15.19 ms（short 档 1.57 ms 的 9.7 倍）是 launch 开销主导的 eager
  decode，不是算力问题——同负载下 vllm（无此 bucket 限制）TPOT 保持 1.91 ms。
  后续引擎优化方向：扩大/分级 seq_len buckets 或引入与上下文长度解耦的 decode-only
  graph（本次按计划不改引擎，仅记录）。
- **TPOT p50 vs p99 的差距暴露长上下文混合批调度**：rapid_llm long 档 p99/p50 达
  1.6–3.3×（如 4B 30.18→100.27 ms），eager decode 与 chunked prefill 交错时 decode 步
  被拉长；vllm 同档 p99/p50 仅 1.02–1.24×。
- **TPS 口径两端一致（完整轮 gen_tokens/墙钟），可直接比较**；TTFT 不可直接横比：
  vllm 的逐请求 TTFT（`first_token_ts−queued_ts`）在 chunked prefill 下是"首 chunk
  延迟"（因此 long 档 vllm TTFT 反而比 short 低），rapid_llm 表内值是全 prefill 完成
  的 1-token 轮批量口径。TPOT 均值同理受口径影响，横比请用 p50/p99。
- **DP2 是干净的有效吞吐扩展**：三个 DP2 点 1.79×–2.11×（64 请求 ≥ 2 副本 ×
  max-num-seqs 32，喂得满）；**TP2 在单卡放得下的模型上全是负收益**（0.64×/0.84×/
  1.04×）——TP 只该当显存开关用，与计划决策一致。
- **EP2 在 batch 8 下不划算**（0.63×）：all-to-all 通信开销大于专家并行带来的 GEMM
  收益，EP 留给高并发特性 A/B 场景。
- **transformers 是量级差距的对照基线**：TPOT 差 8–15×（0.5B medium 41.19 vs
  rapid_llm 15.19 / vllm 1.91 ms），30B MoE 因 Python 逐专家循环 TPOT 91–121 ms。

## 运行注记

1. 首次运行暴露**运行间的显存排空问题**：前一次运行的 0.92-util 显存池在驱动侧回收需 1–2 分钟，
   紧随其后的 TP/NCCL 初始化或 vLLM EngineCore 启动撞上空闲不足即原生崩溃
   （0.5B TP2 运行 crash、多个 vllm 运行 `Engine core initialization failed`）
   修复：`bench_models.run_arm()` 每次运行结束后 `wait_gpu_drain()` 等到显存回到
   套件启动基线 + 512MiB（基线感知，吸收共享宿主上外部进程的不回收显存）。
2. transformers TP2 需要 `accelerate`（此前 venv 重建后未装），已补装 1.14.0。
3. 32k prefill 的 HF generate 有 caching-allocator 碎片问题（17GB reserved-but-unallocated
   导致 4B long OOM）：transformers 运行统一注入
   `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`；4B long 补跑成功并回。
   30B bf16 long TP2 仍 OOM——allocated 67.24GB 后 MoE permute 再要 8GB，reserved-but-
   unallocated 仅 564MB，为**本质性 OOM**（即便无外部残留也差 ~1GB+），按计划记录失败。
4. 数据集长度精确性（vLLM 同款 decode→re-encode 校正）在 Qwen2.5-0.5B tokenizer 上
   128/4096/32768 三档全部 EXACT 零漂移。
